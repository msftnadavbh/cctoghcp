# Plugins: package first, activation later

`examples/plugin/plugin.json` follows the vendored [Agent Plugins 1.0 schema](../../schemas/plugin.schema.json). `python3 -B -m scripts.package_plugin /tmp/checkpoint-skills.zip` creates a deterministic archive with root `plugin.json` and three copied skills. `python3 -B -m scripts.package_plugin /tmp/new-checkpoint-skills --directory` instead produces a **new** unpacked directory; `--directory` is a boolean flag and the output path is positional. Neither installs or enables anything. Static validation uses jsonschema, not a homemade syntax approximation. Generator/schema unit evidence is separate from untested CLI portability. [claim:plugin-generator] [claim:plugin-portability]

Installed 1.0.89 `copilot plugin install --help` omitted local-path syntax although official documentation includes it. Therefore plugin lifecycle was deliberately **not** run. `--plugin-dir` appears in CLI help as a session load option, not evidence that `plugin install` accepts a path. A **source-reviewed but unverified** future candidate is `copilot plugin install /ABSOLUTE/REVIEWED/unpacked-plugin`; only try it after comparing current help and reviewing the **unpacked directory** (not handing `plugin install` a ZIP). If a separately authorized isolated test actually installs, inspect `copilot plugin list`, verify discovery in a *new* session, then check documented `copilot plugin disable NAME`, `enable NAME`, `update NAME`, `uninstall NAME` individually and record what really happened. `update NAME` can fetch newer content and is a separate network/activation decision, **not** a cleanup step. Managed settings can prevent toggling; don't force an outcome. Do not state portability proved by schema validation. [Known discrepancies](../reference/known-discrepancies.md).
