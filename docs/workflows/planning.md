# Planning: review the contract before implementation

Planning depth follows **uncertainty and risk**, not file count. For a small shared guard, a reproduction and one focused check may suffice. For changes across multiple callers, run `/plan` (or `copilot --plan` or Shift+Tab where supported) from [your checkout](../start/use-copilot-in-your-repository.md). Inspect the proposed `plan.md`; edit with Ctrl+Y where supported. Plan mode can still discover/request tools; it is **not** an OS read-only sandbox.

Ask Copilot: “Trace the callers and existing tests for [actual function or task]. Plan the smallest change, affected files, failure/acceptance cases and the test command already used by this repository. Identify assumptions and stop if behavior is ambiguous. Plan only; do not edit or run code.” Replace the bracketed text with your task. Compare citations and commands to your source/CI; don't run an invented command.

A useful plan answers: What behavior changes and stays unchanged? Who calls it? Which files have one edit owner? Which negative case catches a regression? What checks and outputs establish success? What permission or external effect needs approval? When do we stop and ask for a decision? A plan without those answers is not an implementation request. Record a baseline where the existing project offers a suitable check; an unexpected passing/failing baseline needs investigation.

Approve implementation separately, in the agreed files, with manual permissions. Inspect the diff before running newly written tests. `/autopilot` changes turn continuation after a plan, not permissions or the definition of done. [Review](review-and-validation.md) and [permissions](permissions.md) cover those boundaries. For a filled-in **optional practice** contract see [first hour](../start/first-hour.md).

A plan has model cost too; use it when uncertainty or potential rework justify it. When checks repeat without a changed hypothesis or new evidence, pause to save the actual error and baseline, identify a new diagnostic or ask for a decision. A repeated check after new evidence or a code change is useful. [Token economy](token-economy.md) gives examples of bounded prompts.
