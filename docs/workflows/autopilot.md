# Autopilot: agree on an end condition first

Autopilot continues a task; it does not grant write permission, run your trusted checks, limit filesystem access or publish changes. In [your existing repository](../start/use-copilot-in-your-repository.md), use it only when you can name the approved plan, editable paths, test command **actually used by that project** and a clear stopping point. For small changes, manual turns may be simpler.

1. Review `/env`, `/permissions` and `/tasks`; keep manual approvals. Use `/plan` first for a multi-seam change and verify its acceptance cases against actual source. Launch with only the tools needed for the stage (read tools for investigation; add `edit` separately for approved implementation). Don't offer shell just to let the model report a result.
2. If continuation helps, toggle `/autopilot` and request: “Implement the approved plan for [actual task] only in [approved files]. Do not use shell or network. Stop after presenting the diff and naming the existing project checks for me to run; stop earlier on unexpected paths, permissions or unclear behavior.” Replace the placeholders before sending.
3. Inspect each requested write and `/diff`, `/tasks`, `/usage`. Exit, review all changed and new files, then run the **project's** checks yourself. Report observed exits, not Autopilot's completion message. An unexpected change or failing check returns to diagnosis, never a broader grant.

`/settings stayInAutopilot false` changes whether the mode remains on after a task; check the effective setting and mode again on resume. `--max-autopilot-continues 3` limits continuation messages, **not** credits, time, child processes or tools. The preview `/limits set max-ai-credits 30` is a soft limit accounted after a call; inspect `/usage` and your own budget. Esc twice interrupts work, not edits or external effects. [Permissions](permissions.md) and [sessions](sessions-and-context.md) cover the other controls. Headless use is an [optional advanced integration](headless-and-ci.md).
