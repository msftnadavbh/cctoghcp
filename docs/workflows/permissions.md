# Permission design: five distinct questions

Ask: what tools are visible (`--available-tools`/`--excluded-tools`)? What invocations are approved (`--allow-tool`/`--deny-tool`)? Which filesystem paths can be accessed? Which domains/URLs may be contacted? Is the underlying process isolated by an OS/container policy? A read-only agent with `view`, `grep`, `glob` hides write/shell tools; prose saying “read only” does not. `write(relative/path)` can match trailing path components, not necessarily just your current directory; `shell(...)` can write files independently of a `write(...)` rule. The **available tool name** for shell execution in CLI is `bash` (not `shell`); `shell(command)` is a *permission kind*, not a visible tool name. Deny takes precedence over allow, but this is still not a sandbox. [source:programmatic-reference]

`--allow-all` combines all tools, paths and URLs. Keep it only for an explicitly approved disposable environment without credentials, host home, Docker socket or network egress, and never as a workaround for a narrow rule that failed. Captured `help environment` says `COPILOT_ALLOW_ALL` truthy spellings autoapprove tools, but **exact `true` additionally trusts the cwd** and loads its skills/plugins/MCP/hooks; do not export it globally. Native command sandboxing is experimental; Linux bwrap and Windows limits differ, in-process integrations and remote MCP are outside the CLI shell boundary. A VM/container only protects what it really isolates; don't assume `--disallow-temp-dir` isolates the host. [source:cli-reference]

Review credentials, inherited instructions, directories trusted by `--add-dir`, executable binaries and shell profiles before invoking any assistant. A permission decision is per trust boundary, not a replacement for [validation](review-and-validation.md). The repo's [headless wrapper](../../scripts/headless.py) never widens on denial and has no authenticated runtime proof.
