# Permission design: five distinct questions

Separate five controls: available tools, approved invocations, accessible paths, allowed URLs and OS isolation. Use `--available-tools` to limit which tools the model can select and `--allow-tool` or `--deny-tool` to control approval. `view`, `grep` and `glob` exclude edit and shell tools. For shell access, use the tool name shown by your CLI on that platform; `shell(command)` is a permission rule, not an available-tool name. A shell can write files independently of `write(...)` rules, and relative write rules may match trailing path components elsewhere. Prefer explicit paths. Deny rules take precedence; none of these controls provides OS isolation.

`--allow-all` combines all tools, paths and URLs. Keep it only for an explicitly approved disposable environment without credentials, host home, Docker socket or network egress, and never as a workaround for a narrow rule that failed. `COPILOT_ALLOW_ALL` autoapproves tools; **exact `true` additionally trusts the cwd** and loads its skills/plugins/MCP/hooks; do not export it globally. Native command sandboxing is experimental; Linux bwrap and Windows limits differ, in-process integrations and remote MCP are outside the CLI shell boundary. A VM/container only protects what it really isolates; don't assume `--disallow-temp-dir` isolates the host.

Review credentials, inherited instructions, directories trusted by `--add-dir` and shell profiles before execution. Keep [project checks and diff review](review-and-validation.md) separate from tool approval. If an operation is denied, inspect the request rather than broadening permissions automatically.
